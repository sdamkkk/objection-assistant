# 产出格式

处理结果通过 `submit_result` 提交，内容是一个 JSON 对象。界面按这里规定的格式展示，客户经理会直接复制话术去用，所以格式必须严格遵守。

## 一、顶层结构

```json
{
  "task": {
    "deliverables": ["高净值客户版话术", "普通理财客户版话术"],
    "user_situation": [
      { "item": "持有产品", "value": "某某产品（固收+）", "basis": "案例材料" },
      { "item": "买入时间和账户盈亏", "value": "未说明", "basis": "未提供" }
    ],
    "questions": [
      { "id": "Q1", "text": "是不是产品不行", "category": "需要计算或判断" },
      { "id": "Q2", "text": "是不是应该马上赎回", "category": "超出边界" }
    ]
  },
  "objection": {
    "type": "业绩回撤与赎回",
    "title": "某某产品：净值回撤后质疑产品并询问是否赎回",
    "summary": "一句话概括客户的异议：担心什么、质疑什么、想做什么决定"
  },
  "sections": [ ]
}
```

| 字段 | 说明 |
|---|---|
| `task` | 系统对案例和要求的理解。客户经理会先看这一部分，确认系统有没有理解错 |
| `task.deliverables` | 客户经理要的产出物，用应答要求里的说法 |
| `task.user_situation` | 客户的情况，逐项列出。`basis` 只能取三个值：`案例材料`（材料里写了）、`假设`（材料没写，按合理情况假设）、`未提供`（材料没写，也没有假设） |
| `task.questions` | 客户原话里的每个问题。`category` 只能取四个值：`材料可直接回答`、`需要计算或判断`、`材料没有说明`、`超出边界` |
| `objection.type` | 异议类型，取类型指引里的名称；没有对应指引的，填"其他"并写明是什么异议 |
| `objection.title` | 一行标题：产品名称加异议的要点 |
| `sections` | 产出的各个部分，格式见第二节 |

## 二、sections 的格式

```json
{
  "id": "S2",
  "title": "高净值客户版话术",
  "audience": "高净值客户（话术）",
  "kind": "draft",
  "items": [
    {
      "id": "S2-1",
      "text": "话术的一个段落",
      "sources": [
        { "tag": "案例材料", "quote": "从案例材料中逐字摘出的片段" },
        { "tag": "法规原文", "doc": "R06", "quote": "从规则原文中逐字摘出的片段", "note": "第二十四条" },
        { "tag": "业务规则", "note": "P05" }
      ]
    }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `audience` | 这一部分给谁用，只能取四个值：`客户经理`、`高净值客户（话术）`、`普通理财客户（话术）`、`通用` |
| `kind` | 展示形式，只能取五个值，见下表 |

| kind | 用途 | item 要填的字段 |
|---|---|---|
| `list` | 应答要点、需要确认的信息、待核实事项 | `text` |
| `qa` | 追问应对 | `question`、`answer`、`forbidden`（禁止说法）、`escalate`（什么情况下升级） |
| `draft` | 话术 | `text`。一版话术拆成 3–5 段，每段一个 item，按说话的顺序排列 |
| `table` | 对照表 | 在 section 上填 `columns`，在 item 上填 `cells`（个数和 columns 相同） |
| `steps` | 判断过程 | `text`，每个 item 是一步 |

每个 item 都必须有 `sources`，至少一条。

**原文引用会显示为角标。** 来源是【案例材料】【法规原文】的，界面会在这一条后面显示角标 [1][2]，点开能看到原文。系统拿你的 `quote` 到原文里定位，显示的是原文里的那段文字；找不到的，角标标红。所以：

- `quote` 必须是原文里连续的一段，逐字照抄（空格、换行可以忽略），不改写、不省略中间的字、不拼接两处文字。
- 一个片段只证明一件事，短到刚好能支撑这条内容（一般 8–60 字）。一段话依据了几处原文，就写几条 source。
- 话术里的每个数字都要有【案例材料】或【工具计算】的来源；涉及红线的表述要有【法规原文】的来源。

`sources` 的写法：

| tag | 什么时候用 | 还要填什么 |
|---|---|---|
| `案例材料` | 内容直接来自案例材料（客户原话、产品信息、客户情况） | `quote`：逐字摘录的片段，摘录前先用 `find_quote` 确认能找到 |
| `产品资料` | 内容来自产品事实卡（`get_product` 的结果） | `note`：写明字段，比如"本金与收益" |
| `法规原文` | 内容来自规则库里的原始文件 | `quote`：逐字摘录的原文片段，摘录前先用 `find_quote`（填 `doc_id`）确认；`doc`：文件编号，比如"R06"；`note`：条号，比如"第二十四条" |
| `业务规则` | 内容来自易错点说明书、合规口径或客群指引（内部指引，不是原始文件） | `note`：条目编号，比如"P10""C03"，或者"客群指引：高净值客户" |
| `工具计算` | 数字来自工具计算 | `ref`：工具调用的编号，比如"T3"；可以引用多个，用逗号分隔 |
| `AI解读` | 你结合多条信息推出的结论 | `note`：简要说明从哪些事实推出了什么 |
| `材料未说明` | 材料里没有相关信息 | `note`：说明缺的是什么信息 |
| `需求原话` | 内容来自客户经理的应答要求 | `quote`：原话片段 |
| `假设` | 材料没说，按合理情况假设的 | `note`：说明假设的内容 |

## 三、要出哪些 section

先在 `task.deliverables` 里写清楚客户经理要的产出物。按下面的顺序出，前三类按要求出，后三类有内容才出，没有就不出，不要写"无"。

1. **应答要点**（`客户经理`，`list`）：3–5 条，给客户经理开口前看。依次写：客户在担心什么、在问什么；可以确认的事实（带出处）；这次不能说的话是哪几类；开口前最好先确认什么。
2. **高净值客户版话术**（`高净值客户（话术）`，`draft`）：应答要求里要了才出。
3. **普通理财客户版话术**（`普通理财客户（话术）`，`draft`）：应答要求里要了才出。应答要求没说给哪类客户的，两版都出。
4. **追问应对**（`客户经理`，`qa`）：客户很可能接着问的 2–4 个问题，取自类型指引里的"常见追问"。每条都填 `forbidden` 和 `escalate`。
5. **需要向客户确认的信息**（`客户经理`，`list`）：只列会改变说法的信息，每条写明确认后会影响什么。
6. **待核实事项**（`客户经理`，`list`）：需要向产品、合规等部门核实的事。每条写明三点：核实什么；不核实会影响哪句话；向谁核实。

话术的写法：

- 每版 200–350 字，3–5 段，口语化，可以直接说或者稍作修改后发给客户。
- 顺序：回应担心 → 讲事实（产品自己的数据在前，和同类的对比在后，并说明局限） → 回应"产品行不行" → 回应"要不要赎回"（给判断办法，不给结论） → 接下来我能帮您做什么。
- 两版用同一套事实和红线，区别按客群指引来写。
- 正文里不出现来源标签、条目编号和内部用语。
- 合规口径第二部分的三点提示，每一版都要包含。

## 四、提交前自查

- 每个 item 都有 `sources`。
- 话术里的每个数字都来自案例材料、产品事实卡或工具计算结果，指标名称和区间与材料一致。
- 所有 `quote` 都经过 `find_quote` 确认（法规原文的引用要填 `doc_id`）。
- 客户原话里的每个问题都有回应；应答要求里要的版本都出了，没有多出。
- 逐句对照合规口径 C01–C13，两版都没有违反。
- 没有踩易错点说明书里的坑，也没有把不适用的易错点硬套上去。
- 没有补材料里没有的信息（P16）。
